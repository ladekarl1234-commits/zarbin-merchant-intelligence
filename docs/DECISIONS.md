# تصمیم‌های مهم | Decision Log

قالب: **زمینه ← گزینه‌ها ← تصمیم ← چرا ← هزینه**

## 1. محصول: موتور بینش/اقدام به جای داشبورد BI
- زمینه: معیار ۹۰امتیازی «اقدام‌پذیری» و ۴۵امتیازی «UX غیرتکنیکال».
- گزینه‌ها: داشبورد چندنموداره؛ گزارش ثابت؛ فید اقدام رتبه‌بندی‌شده + تحلیل‌های پشتیبان.
- تصمیم: فید اقدام + صفحات تحلیلی پشتیبان + کشوی شواهد.
- چرا: پذیرنده غیرتکنیکال «چه کنم؟» می‌خواهد؛ داور رد «عدد → اقدام → شواهد» می‌خواهد.
- هزینه: تعداد نمودارها عمداً کم است؛ هر نمودار باید به تصمیمی خدمت کند.

## 2. استک: DuckDB + FastAPI + React(Vite)، بدون Docker اجباری
- گزینه‌ها: Next.js SSR + سرویس جدا؛ Streamlit؛ استاتیک کامل (پیش‌محاسبه JSON)؛ استک فعلی.
- تصمیم: پایپ‌لاین DuckDB→Parquet + FastAPI با کوئری زنده + SPA سبک؛ اجرای تک‌فرمان `uv run zarin`.
- چرا: ۲٫۲M ردیف دقیقاً قلمرو DuckDB است؛ کوئری زنده «SQL نمایش‌داده‌شده = SQL اجراشده» را ممکن
  می‌کند (ردیابی واقعی، نه بازسازی‌شده)؛ uv برای داور از Docker کم‌دردسرتر است. Streamlit سقف
  کیفیت UI فارسی/برند را پایین می‌آورد. پیش‌محاسبه کامل، drill-down شواهد را می‌کشت.
- هزینه: یک پروسه پایتون باید بالا باشد؛ Dockerfile هم برای راحتی ارائه شد (مسیر تست‌شده uv است).

## 3. کامیت‌کردن build فرانت‌اند در ریپو
- تصمیم: `zarin/static/` کامیت می‌شود؛ سورس کامل + دستور rebuild هم موجود است.
- چرا: داور بدون Node هم اجرا می‌کند؛ «اجراپذیری» ۳۰ امتیاز دارد.
- هزینه: چند صد کیلوبایت باینری در ریپو و لزوم rebuild پیش از هر کامیت UI.

## 4. تعریف موفقیت = فقط Verified؛ و Paid به‌عنوان حالت مستقل محصول
- زمینه: ۸,۷۰۶ جلسه Paid پول تسویه‌شده دارند اما verify نشده‌اند.
- گزینه‌ها: Paid را موفق بشمار؛ Paid را شکست بشمار؛ حالت مستقل.
- تصمیم: حالت مستقل «تسویه بدون تایید» + کارت اقدام اختصاصی.
- چرا: هم شمردنش به‌عنوان موفقیت و هم شکست، به پذیرنده دروغ می‌گوید؛ جداکردنش یک بینش
  اقدام‌پذیر بدیع است (اصلاح کال‌بک/وریفای؛ مبلغ واقعی، نه برآورد).
- هزینه: قیف ۴مرحله‌ای به توضیح «پول رسید ولی تایید نشد» نیاز دارد — در UI توضیح داده شده.

## 5. «موفقیت اولین تلاش» بر پایه Verified (کشف حین تست بصری)
- زمینه: تعریف اولیه (Verified/Paid) باعث شد اولین‌تلاش (۵۴٫۹٪) از تبدیل نهایی (۵۴٫۵٪) بزرگ‌تر شود.
- تصمیم: متریک کاربر-رو صرفاً Verified-پایه شد؛ پرچم Paid-شمول فقط برای «استخر شکست اول» ماند.
- چرا: عددی که با متریک کنارش جمع‌ناپذیر به نظر برسد اعتماد را می‌کشد.
- هزینه: دو پرچم مجزا در marts؛ با تست قفل شد.

## 6. همتایان: قاعده پلکانی توضیح‌پذیر، نه خوشه‌بندی
- گزینه‌ها: k-means/embedding؛ صنف+باندهای مقیاس/تیکت پلکانی؛ میانگین کل.
- تصمیم: پلکانی (صنف+مقیاس+تیکت ← صنف+مقیاس ← صنف) با کف ۵۰۰ جلسه و سرکوب زیر ۵ همتا.
- چرا: باید بتوان به داور و پذیرنده در یک جمله گفت «چرا این‌ها همتای منند»؛ جعبه سیاه اعتماد
  و امتیاز ردیابی را می‌سوزاند. تمرکز ۷۲٪ GMV در ۵ پذیرنده، میانگین کل را بی‌معنا می‌کند.
- هزینه: در صنف‌های کوچک گروه به کل صنف پس می‌نشیند (در UI گفته می‌شود).

## 7. فرصت بازه‌ای مبتنی بر شکاف، نه «درآمد ازدست‌رفته»
- تصمیم: `شکاف نرخ × جلسه‌ها × تبدیلِ خود × تیکتِ خود`، کف=p50 و سقف=چارک برتر همتایان؛
  شکاف <2pp اصلاً کارت نمی‌سازد.
- چرا: جمع مبالغ ناموفق چندبرابر بیش‌برآورد است و صریحاً در بریف ممنوع بود؛ بازه صادقانه‌تر از
  عدد دقیق دروغین است.
- هزینه: اعداد کوچک‌تر و کمتر «واو»؛ در عوض قابل دفاع در پرسش‌وپاسخ داوری.

## 8. کوپایلوت قطعی، بدون LLM
- گزینه‌ها: اتصال به API مدل زبانی؛ مدل لوکال؛ روتر قصد قطعی.
- تصمیم: روتر قصد فارسی → همان موتور تحلیلی → پاسخ با شواهد.
- چرا: بریف صراحتاً می‌گوید LLM نباید عدد بسازد و پروژه باید برای داور اجراپذیر بماند (بدون کلید/شبکه).
  تجربه «بپرس» حفظ می‌شود و هر عدد ردیابی‌پذیر است.
- هزینه: پوشش پرسش‌ها محدود به قصدهای تعریف‌شده است؛ پرسش خارج از پوشش، راهنمای پرسش‌های
  ممکن را برمی‌گرداند.

## 9. تجزیه تغییر با LMDI
- گزینه‌ها: «تفاوت درصدی» ساده؛ تجزیه باقیمانده‌دار؛ LMDI.
- تصمیم: LMDI (سهم‌ها دقیقاً جمع‌پذیر، بدون باقیمانده) + تجزیه جبری Δتبدیل به چهار نرخ شکست.
- چرا: «سهم هر عامل» فقط وقتی قابل دفاع است که جمعش دقیقاً برابر کل تغییر باشد؛ تست‌شده.
- هزینه: در دوره‌های با GMV صفر تجزیه‌پذیر نیست — UI صادقانه می‌گوید.

## 10. تاریخ‌ها: شمسی در نمایش، میلادی در محاسبه
- تصمیم: همه محاسبات با تاریخ میلادی خام؛ نمایش با `Intl.DateTimeFormat('fa-IR')` (جلالی خودکار)؛
  بازه‌های پیش‌فرض «کل دوره / ۹۰ روز / ۳۰ روز» به‌جای «ماه‌های» ناهم‌راستا با ماه شمسی.
- چرا: برچسب «ماه دی» روی بازه میلادی ژانویه دروغ می‌شود؛ پنجره‌های نسبی این ابهام را ندارند.
- هزینه: انتخاب «ماه شمسی دقیق» به‌عنوان فیلتر وجود ندارد.

## 11. حذف/تغییر نسبت به برخی ایده‌های بریف
- «مقایسه با کسب‌وکارهای همسایه»: داده مکانی وجود ندارد → همتایان رفتاری (بریف خودش همین را پیشنهاد داد).
- RFM کامل: با ۶ ماه داده و کارت‌های فقط-موفق، R و F معنادارند اما M برش‌های کم‌نمونه می‌سازد →
  به «مشتریان ارزشمند غیرفعال» + کوهورت + تمرکز ساده شد؛ برچسب‌گذاری RFM تظاهری حذف شد.
- تشخیص ناهنجاری سری‌زمانی خودکار: با ۶ ماه داده و تمرکز شدید، نرخ هشدار کاذب بالا می‌رفت →
  به‌جایش تجزیه قطعی + کارت تغییر ≥۱۰٪ (آستانه‌دار).
